# 00. Сводка разведки (промежуточная)

Дата: 2026-08-24. Статус: **разведка завершена, открытых вопросов нет** — амо, бот, календарь, чат и Excel партнёра разобраны; метрики M1–M9 посчитаны; все вопросы закрыты ответами владельца или данными. roptick исключён решением владельца; чат выполненных заказов исключён (источник истины — БД бота).

Ковровый поток (важное уточнение к брифу): заказ партнёру передаётся **телефонным звонком под диктовку**, а не через чат; чат — внутренний слой (скрин заметки для владельца, иногда забывают → сделка в амо не заводится → те самые ~4-10% провалов матчинга по коврам).

## Главные цифры

- **M1–M4 (календарь → амо): 87% событий связываемы автоматически.** 70% — ровно одна сделка по телефону, 17% — выбирается датой; 8% — неоднозначно, 4% — сделки нет, 2% — нет телефона в событии. Телефон извлекается из 98,5% событий (посимвольным парсером; простая регулярка теряет на порядок больше).
- **M5 (бот → амо): 92% заказов проводимы автоматически.** 73% находят ровно одну сделку по телефону, ещё 19% — однозначно по дате. 8% (≈1 заказ в неделю) требуют человека: половина — сделки в амо вообще нет, половина — неоднозначная дата.
- **M7 (Excel партнёра → амо): 90% строк находят сделку в ковровой воронке**, 6% — сделка есть, но заведена в воронках уборки, 4% — сделки нет. Телефон распознан в 51/51 строках. Отказы партнёр выгружает отдельным отчётом с причинами.
- **M6 (Excel партнёра ↔ чат): всего 22%** — потому что заказы уходят в чат скриншотами; но скриншоты — это карточки событий Google Calendar, т.е. чат для заказов лишь дублирует календарь. **M9 = 0%**: «дата днём недели без числа» в ковровых сообщениях не встретилась (16 текстов за 8 мес.), даты явные «дд.мм».
- **Сквозной вывод: «телефон + дата» работает на всех посчитанных стыках (87–92%).** Провалы «сделки нет» (~4%) на разных стыках дают одних и тех же клиентов — это устойчивый контур «клиент мимо CRM», для него нужен сценарий создания сделки с нуля. Чат как машиночитаемый источник не нужен: заказы читаются из календаря, выполнение — из БД бота, ковры — из Excel партнёра; за чатом остаются только отмены (но их надёжнее ловить по удалению события в календаре).
- Телефон есть у 97,4% сделок амо; дубли контактов — 1,4% телефонов (выборка 90 дней).
- Из 65 кастомных полей сделки живых 12, мёртвых 53.
- Объём за 90 дней: 797 сделок в амо, 171 заказ в боте, 897 задач (в основном автозадачи робота), 920 примечаний (ручных — 14).

## Как устроено на самом деле (ключевые факты)

1. На один заказ в амо живут **две сделки**: успешная в первичной воронке + автосделка в воронке реализации, которую создаёт сейлзбот с ветвлением по услуге (мебель/клининг → «Воронка для реализации», ковры → «Ковры Кристал»). Подтверждено владельцем и данными («Автосделка: Сделка #…»). Матчер должен это учитывать (приоритет воронки реализации).
2. Автозадачи ставит робот (Digital Pipeline): «1-ый звонок» (сразу), «Назначь мастера + ПРОВЕРЬ КАЛЕНДАРЬ» (0–72 ч), «Выполни заказ» (+24 ч), «Получить ОС + начислить бонусы 300 + взять ДР» (+24 ч). Текст задачи «Получить ОС» дублирует то, что уже делает бот.
3. Ковровый контур — воронка «Ковры Кристал» (партнёр «Кристалл», info.kristall-nn@mail.ru); вторая ковровая воронка — мёртвый рудимент.
4. Отмена по факту (подтверждено владельцем): удалить запись в календаре + сообщение в чат, дальше владелец руками закрывает сделку с причиной (окончательно) или откатывает в «Заказ оформлен» (перенос) — комментарий «отменен» из брифа не пишется. Значит, надёжный сигнал отмены для автоматики — календарь/чат, не примечания амо.
5. Бот: «Заказ №N» = первичный ключ таблицы orders. Ручной импорт из амо — команда `/import_amocrm` (CSV → dry-run → подтверждение), матчит по телефону, схлопывает сделки одного клиента.
6. **Риск: нормализация телефона реализована 5 разными способами** в разных частях кода (включая regex, не ловящий номера с 9 без префикса, и SQL/Python-расхождение NULL/мусор). Для сквозного матчинга нужен один канон.
7. Excel партнёра пригоден для матчинга: свой ID заказа, телефон в едином формате, суммы, даты забора/сдачи. Похож на месячный, а не недельный.
8. Встраивать интеграцию есть куда: в боте отработанный шаблон (пакет + гейт + ensure_schema + polling-цикл с курсорами в БД + очередь notification_outbox); 11 текстов под календарный флоу уже заготовлены в notification_rules.json.
9. Календарь: формат «Префикс! Услуга, Имя» устойчив (94%), префиксы = районы города; не-заказы отличаются маркером «⛔️» (89% случаев); отмена = удаление события (для её отлова интеграции нужен инкрементальный sync, обычная выдача удалённые не показывает); 18% событий правятся спустя >48 ч (переносы/дописывания); календарь ведётся из-под одного аккаунта raketaclean52@gmail.com.

## Риски

1. Разнобой нормализации телефонов (п.6) — прямая угроза сквозному ключу.
2. «Дата и время заказа» заполнена в 78% сделок и иногда протухшая (2022/2024 в живых сделках) — как второй ключ работает, но не абсолютна.
3. 4–8% заказов бота не имеют сделки в амо — контур «сделку придётся создавать» обязателен.
4. Токен амо долгоживущий и **строго read-only** (подтверждено владельцем) — для автоматического проведения сделок понадобится новая интеграция с правом записи. При протухании токена polling молча останавливается (уже известное ограничение).
5. Digital Pipeline настройки не выгружаются по API — автоматизацию восстановили по следам задач; перед изменением этапов нужно перепроверить в UI.
