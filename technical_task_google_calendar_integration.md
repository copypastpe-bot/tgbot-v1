## 1) Цель
Перевести создание заказов в поток «Google Calendar -> БД -> Telegram-бот», чтобы:
- заказы автоматически появлялись в БД из календаря;
- исполнитель выбирал заказ из списка (без ручного ввода клиента/адреса);
- клиент получал напоминание за 24 часа;
- по реакциям/не-реакциям клиента шли автоматические эскалации админам.

## 2) Зафиксированные решения
- Календарь: один аккаунт Google Calendar, один календарь на оба вида работ.
- Интеграция: backend подключается к Google Calendar API.
- Синхронизация: polling каждые 2 минуты.
- Источник истины по заказам: календарь (односторонне calendar -> bot).
- Идентификатор внешнего заказа: `google_event_id`.
- Цвет события НЕ разбирается. Причина: зелёный означает и «два мастера», и «химчистка + уборка»
  (различие только в пометке), автоматический разбор давал бы ошибки с попаданием заказа не в тот
  финансовый контур.
- Исполнители при импорте не назначаются. Исполнитель сам выбирает свой заказ.
- В списке показывать непроведённые заказы на сегодня/завтра/послезавтра.
- Максимум 10 заказов в списке.
- Вид работ (химчистка / клининг) определяется ролью того, кто нажал `Выполнить`.
- Одна карточка календаря может быть проведена максимум по одному разу в каждом контуре.
  Парная карточка «химчистка + уборка» даёт два заказа: один в `orders`, один в `cleaning_orders`.
- Если заказ уже проведён, изменения календаря его не меняют.
- Если заказ не проведён и в календаре отменён/удалён, заказ архивируется (клиент остаётся в БД).
- Клиент подтверждает визит словами `да` / `нет`.
- Напоминание клиенту одно — за 24 часа до визита.
- Админ-уведомления: в личные сообщения админов по `ADMIN_IDS`/`ADMIN_TG_IDS`.
- Повтор админ-эскалации: каждые 10 минут до нажатия `Я связался`.
- Таймзона: `Europe/Moscow`.

## 3) Входные данные события календаря
Пример карточки:
- `summary`: `Авт! Диван и ковер Наталья`
- `start/end`: дата и время
- `location`: адрес
- `description`: услуги + строка с именем и телефоном, например `Наталья +79519177091`

Что извлекаем:
- `google_event_id`
- `start_at`, `end_at`
- `client_name`
- `client_phone` (нормализовать до `+7XXXXXXXXXX`)
- `address`
- `services_text`
- raw payload (для трассировки)

Поле `colorId` сохраняем в `payload_json` для трассировки, но в логике не используем.

## 4) Область работ (MVP)
1. Доступ к календарю через сервисный аккаунт Google.
2. Синхронизация Google Calendar в БД.
3. Кнопка `Заказы сегодня` и карточка заказа для исполнителя.
4. Проведение заказа по существующему flow с минимальными изменениями.
5. Напоминание клиенту за 24 часа.
6. Фиксация реакции клиента (подтверждение/отмена/нет ответа).
7. Эскалация админам с кнопкой `Я связался` и повторами до ack.

## 5) Не входит в MVP
- Двусторонняя синхронизация (bot -> calendar).
- Автоматическое назначение исполнителя из календаря.
- Разбор цвета события.
- Второе напоминание в день визита.
- Сложная NLP-классификация ответов клиента.
- Рефакторинг монолита `bot.py`.

## 6) Изменения схемы БД

### 6.1 Таблица `calendar_orders`
Поля (минимально необходимые):
- `id bigserial primary key`
- `google_event_id text not null unique`
- `status text not null default 'active'`
  Допустимые: `active`, `archived`, `completed`
- `start_at timestamptz not null`
- `end_at timestamptz`
- `timezone text not null default 'Europe/Moscow'`
- `title_raw text`
- `description_raw text`
- `location_raw text`
- `client_name text`
- `client_phone text`
- `address text`
- `services_text text`
- `client_id bigint references clients(id) on delete set null`
- `google_updated_at timestamptz`
- `payload_json jsonb not null default '{}'::jsonb`
- `archived_reason text`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Индексы:
- `(status, start_at)`
- `(client_id)`

Статус `completed` выставляется, когда карточка проведена хотя бы в один контур.
Карточка остаётся доступной для проведения во второй контур, пока в нём нет своего заказа.

### 6.2 Таблица `order_confirmations`
Поля:
- `id bigserial primary key`
- `calendar_order_id bigint not null unique references calendar_orders(id) on delete cascade`
- `state text not null default 'pending'`
  Допустимые: `pending`, `confirmed`, `cancelled`, `no_response`, `delivery_failed`, `acked`
- `reminder_due_at timestamptz not null`
- `reminder_sent_at timestamptz`
- `delivery_state text`
- `delivery_checked_at timestamptz`
- `response_text text`
- `responded_at timestamptz`
- `admin_alert_sent_at timestamptz`
- `next_repeat_at timestamptz`
- `admin_ack_by bigint`
- `admin_ack_at timestamptz`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Индексы:
- `(state, next_repeat_at)`
- `(reminder_due_at)`

Подтверждение одно на карточку календаря, а не на заказ: клиенту незачем получать
два напоминания о парной работе.

### 6.3 Связь с уже существующими заказами
В `orders` добавить:
- `calendar_order_id bigint unique references calendar_orders(id) on delete set null`

В `cleaning_orders` добавить:
- `calendar_order_id bigint unique references calendar_orders(id) on delete set null`

Назначение:
- уникальность в каждой таблице исключает двойное проведение карточки внутри одного контура;
- две независимые ссылки разрешают парное проведение «химчистка + уборка».

## 7) Доступ к календарю

- У проекта уже есть сервисный аккаунт Google (`docs/Sheets.json`), он читает таблицу промо-текстов.
- Календарь необходимо расшарить на адрес этого сервисного аккаунта с правом чтения,
  либо завести отдельный сервисный аккаунт под календарь.
- Требуемый scope: `https://www.googleapis.com/auth/calendar.readonly`.
- Путь к ключу и идентификатор календаря вынести в env: `GOOGLE_CALENDAR_ID`,
  `GOOGLE_CALENDAR_CREDENTIALS` (по умолчанию — существующий файл ключа).
- Секреты в репозитории не хранить.

## 8) Синк календаря (backend, polling)

### 8.1 Интервал
- Каждые 2 минуты.

### 8.2 Алгоритм
1. Получить изменения событий календаря.
2. Для каждого события:
- извлечь данные;
- нормализовать телефон;
- найти/создать клиента по телефону;
- upsert в `calendar_orders` по `google_event_id`.
3. Если событие отменено/удалено:
- если связанных заказов нет -> `calendar_orders.status='archived'`;
- если заказ уже проведён хотя бы в один контур -> проведённое не менять.
4. Если событие изменилось (дата/время/адрес/текст):
- обновить `calendar_orders`, но только если ещё не проведено ни в один контур.

### 8.3 Идемпотентность
- Все операции синка должны быть безопасны к повтору.
- Ключ дедупликации: `google_event_id`.

## 9) Изменения в боте (flow исполнителя)

### 9.1 Кнопка `Заказы сегодня`
Добавляется в меню мастера и в меню бригадира клининга.
При нажатии показывается список календарных заказов:
- `status` не `archived`
- дата в диапазоне [сегодня, +2 дня] по MSK
- в контуре нажавшего заказ ещё не проведён
- лимит 10
Каждый пункт списка — inline-кнопка.

### 9.2 Карточка заказа
При выборе пункта открывается карточка с информацией по заказу:
дата и время, адрес, клиент, телефон, услуги.
Inline-кнопки: `Выполнить`, `Назад`.

### 9.3 Определение контура
При нажатии `Выполнить` смотрим роль нажавшего в `staff`:
- `master` -> заказ проводится в химчистку (`orders`);
- `cleaner` -> заказ проводится в клининг (`cleaning_orders`).

Роли не пересекаются: на 2026-08-12 в `staff` 7 `master` и 2 `cleaner`, пересечений нет.

Роли `admin` и `superadmin` заказы не проводят: кнопка `Заказы сегодня` им не показывается,
нажатие `Выполнить` с этих ролей отклоняется. Неоднозначности контура не возникает.

### 9.4 После выбора
- в FSM сохранить `calendar_order_id`, `client_id`, `phone`;
- далее оставить существующий flow соответствующего контура:
  1. телефон (можно предзаполнить/подтвердить)
  2. сумма чека
  3. доп. продажа (да/нет; если да -> сумма)
  4. списание бонусов
  5. способ оплаты
  6. добавить второго мастера (опционально, покрывает «зелёные» парные работы)
  7. подтверждение

### 9.5 Финал проведения
- создать запись в `orders` или `cleaning_orders` с `calendar_order_id`;
- выставить `calendar_orders.status='completed'`;
- карточка остаётся доступной для проведения во второй контур, если там заказа ещё нет.

## 10) Контур напоминания клиенту за 24 часа

### 10.1 Постановка напоминания
Для каждого `calendar_order` в `active`:
- `reminder_due_at = start_at - interval '24 hours'`
- создать/обновить `order_confirmations`.

### 10.2 Отправка
Когда `now() >= reminder_due_at` и `reminder_sent_at is null`:
- отправить сообщение клиенту через текущую Wahelp-логику;
- сохранить `reminder_sent_at` и `delivery_state`.

### 10.3 Текст
Текст уже описан в `docs/notification_rules.json`, цепочка `visit_reminders`, шаг 1:

```
Напоминание о визите завтра:
📅 {{date}} в {{time}}
📍 {{address}}

Мастер: {{master_name}} ({{master_phone}})
Подтвердите, пожалуйста, что будете на месте.
```

При реализации:
- завести отдельный `event_key` для этого напоминания и проверить, что он вызывается из кода
  (иначе текст останется мёртвым, как сейчас);
- строку про мастера убрать или заменить: исполнитель на момент напоминания неизвестен,
  он назначается только при проведении заказа;
- заменить формулировку «Подтвердите, пожалуйста» на явную просьбу ответить `да` или `нет`;
- решить, приклеивать ли блок контактов (`SERVICE_FOOTER_KEYS` в `crm/wahelp_dispatcher.py`).

### 10.4 Реакции клиента
Обработчик входящих (`handle_wahelp_inbound` в `bot.py`) классифицирует ответ:
- `confirmed` — `да`, `буду`, `подтверждаю` и близкие формы;
- `cancelled` — `нет`, `отмена`, `не смогу` и близкие формы;
- `other` — всё остальное.

ВАЖНО: цифры `1`-`5` и слово `STOP` уже заняты другими сценариями.
Порядок разбора входящего сообщения на 2026-08-12:
1. цифра `1`-`5` при ожидающей оценке заказа -> оценка работы;
2. `1` в остальных случаях -> интерес к промо;
3. `STOP` -> отписка от рассылки.
Классификация подтверждения визита должна встраиваться в эту цепочку, не ломая её.

## 11) Контур эскалации админам

### 11.1 Когда эскалировать
Эскалация обязательна, если:
- клиент явно отменил (`cancelled`), или
- через 3 часа после `reminder_sent_at` нет ответа (`no_response`), или
- доставка напоминания неуспешна (`delivery_failed`).

### 11.2 Формат алерта
Отправлять каждому админу в личку:
- клиент, телефон, адрес, время заказа, причина эскалации.
- inline-кнопка: `Я связался`.

### 11.3 Повторы
- если никто не нажал `Я связался`, повторять каждые 10 минут.
- остановка повторов только после `admin_ack_at`.

## 12) Логирование и диагностика
Нужно логировать:
- поллинг календаря (успех/ошибка, количество событий);
- парсинг карточек (особенно ошибки телефона);
- изменения статуса `calendar_orders`;
- отправку напоминаний;
- классификацию ответов;
- отправку/повторы/ack админ-эскалаций.

## 13) Критерии приёмки
1. Новое событие календаря появляется в `calendar_orders` максимум через 2 минуты.
2. Изменение даты/времени в календаре отражается в `calendar_orders`, если заказ не проведён.
3. Отменённый непроведённый заказ получает `status='archived'` и исчезает из списка.
4. Мастер по кнопке `Заказы сегодня` видит список (до 10 шт), открывает карточку и проводит
   заказ в химчистку без ручного ввода данных клиента.
5. Бригадир клининга тем же путём проводит заказ в клининг.
6. Парная карточка проводится дважды — по разу в каждый контур; третье проведение невозможно.
7. Повторное проведение карточки в тот же контур невозможно.
8. За 24 часа уходит напоминание клиенту.
9. Ответ клиента `да` / `нет` фиксируется в `order_confirmations` и не ломает разбор оценок и промо.
10. При отмене / no-response (3ч) / delivery_failed уходит алерт всем админам.
11. Повтор алерта идёт каждые 10 минут до нажатия `Я связался`.

## 14) Порядок реализации
1. Доступ к календарю (расшарить, env, проверка чтения).
2. Миграции БД (`calendar_orders`, `order_confirmations`, `orders.calendar_order_id`,
   `cleaning_orders.calendar_order_id`).
3. Backend polling + parser + upsert/archiving.
4. Кнопка `Заказы сегодня`, список и карточка заказа.
5. Привязка проведения к `calendar_order_id` в обоих контурах.
6. Job напоминаний за 24 часа.
7. Классификация ответов клиента (`да` / `нет`) в существующей цепочке разбора.
8. Эскалации и цикл повторов до ack.
9. Финальная диагностика и smoke-check на проде.

## 15) Технические ограничения
- Правки должны быть минимальными и локальными.
- Не отключать существующую защиту от бесконечных попыток доставки.
- Секреты/ключи не хранить в репозитории.
- При расхождении схемы — доверять фактической БД, не только migration-файлам.
- Учитывать общий лимит отправок `DAILY_SEND_LIMIT` (на 2026-08-12 — 60/сутки).
  При текущем потоке ~1.8 заказа в день напоминания добавляют ~2 сообщения в сутки.
