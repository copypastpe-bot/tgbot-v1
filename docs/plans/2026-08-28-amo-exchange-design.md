# Автообмен amoCRM → база бота

Дата: 2026-08-28. Статус: дизайн согласован владельцем, план работ следующий шаг.

## Зачем

Владелец раз в неделю выгружает из амо сделки в CSV и загружает в бота руками.
Это ручная работа и задержка до недели: клиент, записанный сегодня, попадёт
в базу только после следующей выгрузки. Из-за этой задержки невозможен
разговор с клиентом до работы (см. `2026-08-28-client-messaging-design.md`).

Плюс нынешняя загрузка молча теряет часть данных: код ищет колонки по названиям
(«Основной контакт», «Бонусные баллы (контакт)»), а шаблон выгрузки в CRM с тех
пор изменился — эти колонки называются иначе, и поля не доезжают. Импорт при
этом отрабатывает «успешно».

## Что делает обмен

**Главное: пополняет базу лидов и дописывает клиентам адрес, услугу и имя.**

Раз в минуту робот спрашивает амо, какие сделки первичной воронки закрылись
с прошлой проверки.

- **Закрылась успешно** («Передано в работу», статус 142) → человек попадает
  в базу как **клиент**. Это момент оформления заказа, а не его выполнения:
  именно тогда позже понадобится написать клиенту подтверждение.
- **Закрылась отказом** (143) → попадает как **лид**, но только если его
  в базе ещё нет.

## Правила данных (решения владельца 2026-08-28)

| Поле | Правило |
|---|---|
| Телефон | ключ сопоставления; записи нет — заводим |
| Имя | дописываем, если в базе пусто |
| Адрес заказа | дописываем |
| Услуга | дописываем |
| Район | не трогаем |
| Дата последнего заказа | не трогаем |
| Бонусы | **никогда** — их ведёт бот |
| День рождения | **никогда** — его ведёт бот |
| Статус | успех → клиент; отказ → лид, только для новых записей |

Направление данных важно: бонусы, день рождения и дата заказа рождаются в боте
и уходят в базу оттуда. Обмен, который их «обновляет» из CRM, затирал бы
свежее старым.

### Два защитных правила

1. **Понижения статуса не бывает.** Кто уже клиент — остаётся клиентом.
   Постоянный клиент, узнавший цену и не заказавший, не превращается в лида.
2. **Отказная сделка существующего клиента не меняет ничего**: ни статуса,
   ни адреса, ни услуги, ни имени. Человек ничего не заказывал — менять нечего.

Сопоставление всегда по номеру телефона, поэтому вторая запись на того же
человека не появляется, даже если в CRM он записан под другим именем.

## Устройство

Живёт в рабочем боте: он хозяин таблицы `clients` и пишет в неё по праву.
Админ-боту это запрещено жёстким правилом, и правило остаётся в силе.

Поля берутся из амо напрямую по их идентификаторам, а не по названиям колонок
выгрузки. Это убирает целый класс тихих потерь: правка шаблона выгрузки в CRM
больше ни на что не влияет.

Робот держит закладку — до какого момента изменения разобраны. Закладка
сдвигается только после того, как пачка обработана целиком, поэтому сбой или
перезапуск означает «продолжим с того же места», а не «пропустим».

История не переносится: в работу идут только сделки, закрывшиеся после
включения. Прошлое владелец уже загрузил руками.

Ручная загрузка CSV остаётся как запасной путь и не удаляется.

## Сбои

- Амо недоступна — ждём следующей минуты, закладка не двигается, ничего
  не теряется.
- Одна плохая сделка не роняет проход: остальные обрабатываются, сбойная
  возвращается в следующий раз.
- Сделка без телефона пропускается (в CSV такие тоже пропускались, молча —
  здесь их надо считать и показывать владельцу).

## Включение

Свой выключатель, по команде владельца, сначала в режиме репетиции: робот
показывает, кого он завёл бы и с каким статусом, ничего не записывая. Тот же
порядок, что у календаря: репетиция → проверка глазами → боевой режим.

## Открытые вопросы

- Нужна ли владельцу ежедневная сводка обмена (сколько клиентов и лидов
  добавлено, сколько пропущено без телефона). Не решено.
- Как именно спрашивать амо об изменениях: фильтр по дате изменения сделки
  плюс фильтр по воронке и статусу — проверить на живом API при реализации.
